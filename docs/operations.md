# 運用手順 — PDCAサイクルと意思決定ゲート

## 自動運用(Claude Code クラウドRoutine設定済み・2026-08-06)

| Routine | スケジュール | 内容 |
|---|---|---|
| NAR日次データ収集 | 毎日 22:45 JST | `scripts/daily_ingest.py` で当日全NAR開催の成績・払戻・式別票数を `data/nar/` に収集しコミット&プッシュ |
| 週次PDCAレポート | 毎週月曜 9:30 JST | 蓄積データのカバレッジ・オッズ帯別回収率・プール分析を `docs/journal/YYYY-WW.md` に自動作成。500レース超で実データのモデル検証(対数尤度判定)を開始 |

- どちらも新しいクラウドセッションとして起動し、結果はプッシュ通知される
- 停止・変更は claude.ai の Routines 管理画面から(またはClaudeに依頼)
- 自動セッションは AGENTS.md のガードレール下で動き、**馬券購入は行わない**

目的: 「当たった/外れた」の感想ではなく、**較正と対数尤度**で回る
週次PDCAを定義する。Claude Code と Codex の2エージェント体制で、
実装と敵対的レビューを分離する。

## 週次サイクル

### Plan(月曜)
- 仮説は `docs/strategy.md` §6(未解決の論点)から1つ選ぶ/追記する。
- 検証条件を**実行前に**固定してコミットする:
  対象期間・分割点・特徴量リスト・EV閾値・購入ルール。
  (実行後に条件を動かした結果は「探索」であり「検証」ではない —
  多重比較の罠。docs/research/ml-implementations.md §4)

### Do(火〜金)
- 実装エージェント(どちらか一方)が特徴量/モデルを実装し、
  PIT特徴量(`features.py`)+時系列分割でバックテスト。
- 新しいレースが消化されたら `store.py` にデータ追加、
  ペーパートレード(`PaperBroker`)は毎開催日回し続ける。

### Check(土日レース後)
必ず以下の順で見る(回収率は最後):
1. **対数尤度**: 評価期間で 結合(α,β) > 市場単体 か?
   (`model.mean_race_log_likelihood` / `blend.log_likelihood`)
2. **α の値**: `fit_blend_weights` の α が安定して正か?
   α≈0 ならモデルに市場超の情報は無い。
3. **較正**: `calibration.reliability_table` の gap が大きいビンはどこか。
   そのビンの賭けを止めるか、確率を較正し直す。
4. **ビン別回収率**: `roi_by_bin` でEV帯ごとの実回収率。
   高EV帯ほど回収率が高い単調性が崩れていたら確率がおかしい。
5. **ペーパー実績 vs バックテスト**: `keiba summary` の実回収率が
   バックテストの想定レンジ内か。乖離はスリッページ(オッズ変動)か
   リークのどちらかを疑う。
- **レビューエージェント(実装していない方)** が差分と結果を敵対的に
  レビュー: 「この改善はリークでは?」「条件を後から動かしていないか?」
  「サンプル数で説明できる差では?」を必ず問う。

### Act(日曜夜)
- 判定は3択のみ: **継続 / 修正 / 停止**。根拠をコミットメッセージに残す。
- 撤退基準(いずれかに該当したら**停止が正解**):
  - 結合の対数尤度が市場単体を4週連続で上回れない
  - ペーパー実績がバックテスト想定を大きく下回り続ける(乖離の原因不明)
  - ドローダウンが事前設定値(推奨: 資金の30%)に到達
  - キルスイッチを引く判断を迷ったら引く(再開はレビュー後)

## 実弾移行の条件(全て満たすまでペーパーのみ)

1. ペーパートレードで数百レース以上、上記Checkを全て通過
2. 対数尤度・較正・回収率の3指標が安定
3. `ExecutionGuard` の上限(日次投下額・件数)を資金に対して保守的に設定
4. 全購入が `store.bets` に自動記録される経路のみ使用
   (税務: 雑所得認定には購入記録の完全性が必須 — docs/research/tax.md)
5. 実弾Adapterは投票照会との突合(verify)を実装済みであること
   (JRAは連携ソフト投票を「無保証」としている — docs/research/automation-tos.md)

## 資金管理の既定値

- フラクショナルケリー: 1/4(`DecisionPolicy.kelly_fraction=0.25`)
- 1点 ≤ 資金の1% / 1レース ≤ 3% / 日次上限は `ExecutionGuard` で別途強制
- オッズ帯: 1.5〜100倍のみ(較正外領域を避ける)
- これらを緩める変更は「Checkを3サイクル連続で通過した後」のみ検討

## 記録の規律

- 全ての検証はコミットとして残す(条件固定→実行→結果の順が履歴で追えること)
- 週次のCheck結果は `docs/journal/YYYY-WW.md` に1ファイルずつ残す
- 「なぜ賭けなかったか」も記録する(rejected ordersはExecutionResultにある)
